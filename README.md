# AI-помощник по входящим заявкам (MVP)

Учебный прототип для интенсива: одна веб-страница, которая отправляет текст заявки
в **GigaChat API**, возвращает готовую карточку для менеджера и сохраняет результат
в **Битрикс24**.

Что делает помощник:

- определяет суть запроса;
- квалифицирует лид: **целевой / нецелевой / неясно**;
- выделяет известные данные и то, чего не хватает;
- предлагает следующий шаг менеджера;
- готовит черновик ответа клиенту;
- отмечает заявки, которые должен разбирать человек (жалобы, конфликты, нестандартные случаи);
- сохраняет заявку в Битрикс24: контакт, сделку, таймлайн, задачу и уведомление.

Проект не использует собственную базу данных, авторизацию и мессенджеры — это
осознанное ограничение MVP. Интеграция с Битрикс24 опциональна: без `B24_URL`
приложение работает как раньше, только без сохранения в CRM.

---

## 1. Что понадобится

- Python 3.10 или новее (проверено на Python 3.14).
- Интернет: приложение обращается к GigaChat API.
- Аккаунт и ключ авторизации GigaChat API.
- Портал Битрикс24 и входящий вебхук с правами `crm`, `task`, `im`
  (для сохранения заявок; без него приложение тоже работает).
- 10–15 минут на настройку.

Все библиотеки ставятся одной командой, ничего компилировать не нужно.

## 2. Быстрый старт (Windows)

### Шаг 1. Откройте терминал в папке проекта

В VS Code: **File → Open Folder** → выберите папку `intens2010`, затем
**Terminal → New Terminal**.

### Шаг 2. Создайте виртуальное окружение (рекомендуется)

Виртуальное окружение — отдельная папка с библиотеками только для этого проекта.
Так они не конфликтуют с другими программами.

```powershell
python -m venv .venv
.venv\Scripts\activate
```

Если PowerShell ругается на запуск скриптов, выполните один раз:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

и повторите активацию. В начале строки терминала появится `(.venv)`.

### Шаг 3. Установите библиотеки

```powershell
pip install -r requirements.txt
```

### Шаг 4. Проверьте файл настроек `.env`

В проекте уже есть файл `.env`, созданный из шаблона. Если его нет — создайте:

```powershell
copy .env.example .env
```

macOS / Linux:

```bash
cp .env.example .env
```

### Шаг 5. Вставьте ключ GigaChat

1. Откройте [личный кабинет GigaChat API](https://developers.sber.ru/studio/workspaces/my-space/get/gigachat-api).
2. Создайте проект **GigaChat API** (если его ещё нет).
3. Нажмите **«Настроить API»**.
4. Скопируйте **ключ авторизации (Authorization key)**. Он показывается один раз.
5. Откройте файл `.env` в VS Code и вставьте ключ:

```dotenv
GIGACHAT_CREDENTIALS=сюда_вставить_ключ_без_слова_Basic
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat-2-Pro
```

Сохраните файл: `Ctrl + S`.

> **Ключ — это секрет.** Не отправляйте его в чаты, не показывайте на скриншотах
> и не храните в коде. Файл `.env` уже добавлен в `.gitignore` и не попадёт в git.

### Шаг 6. Скачайте сертификат Минцифры

GigaChat использует сертификат Национального удостоверяющего центра, которого
по умолчанию нет в Python. Без него появится ошибка `CERTIFICATE_VERIFY_FAILED`.

```powershell
python download_cert.py
```

Сертификат сохранится в `certs/russian_trusted_root_ca_pem.crt`, приложение
подхватит его автоматически. Дополнительно используется системное хранилище
сертификатов Windows: если HTTPS проверяет антивирус или корпоративный прокси,
его корневой сертификат достаточно установить в системе. Отключать проверку SSL
не нужно.

Если автоматическое скачивание не сработало, скачайте корневой сертификат вручную
с [gosuslugi.ru/crt](https://www.gosuslugi.ru/crt) и положите файл в папку `certs`
с именем `russian_trusted_root_ca_pem.crt`.

### Шаг 7. Подключите Битрикс24 (опционально)

Интеграция включается, если в `.env` заполнен `B24_URL`. Без него приложение
работает как раньше: анализ и карточка на странице остаются доступны.

1. В Битрикс24 откройте **Разработчикам → Другое → Входящий вебхук**.
2. Отметьте права **`crm`**, **`task`**, **`im`** и сохраните вебхук.
3. Скопируйте URL вида `https://<портал>.bitrix24.ru/rest/<id>/<токен>/`
   и вставьте его в `.env`:

```dotenv
B24_URL=https://ваш-портал.bitrix24.ru/rest/1/токен/
```

4. Убедитесь, что CRM работает в **простом режиме без лидов**. Если включён
   классический режим с лидами, приложение вернёт статус
   `unsupported_mode` и не будет создавать контакт и сделку.
5. Создайте пользовательские поля (скрипт можно запускать повторно):

```powershell
python setup_bitrix24.py
```

Скрипт создаст 14 полей контакта `UF_CRM_AI_LAST_*` и 12 полей сделки
`UF_CRM_AI_*`, проверит режим CRM и не будет пересоздавать существующие поля.

6. Перезапустите сервер. В карточке заявки появятся статус сохранения и ссылки
   на контакт и сделку.

> `B24_URL` — секрет. Он не выводится в логи, ответы API и браузер. Не публикуйте
> вебхук и не добавляйте его в git.

### Шаг 8. Запустите приложение

```powershell
python run.py
```

В терминале появится ссылка. Откройте её в браузере:

```
http://127.0.0.1:8000
```

Остановить сервер: `Ctrl + C` в терминале.

> После изменения `.env` сервер нужно перезапустить: настройки читаются при старте.

## 3. Как проверить, что всё работает

На странице есть форма с полями «Имя клиента», «Телефон», «Почта» и «Заявка»,
а также три кнопки с тестовыми заявками. Нажмите кнопку или заполните форму сами,
затем нажмите **«Обработать заявку»**.

После успешной обработки под формой появляется блок **«Что уходит в нейросеть»**.
В нём показан точный текст, который получила модель: персональные данные уже
заменены токенами, а рядом перечислено, сколько сущностей каждого типа
замаскировано. Текст можно скопировать кнопкой «Скопировать».

### Сценарий 1 — полная целевая заявка

«Альфа-Логистик», 40 рабочих мест, бюджет 1,5 млн ₽, контакты заполнены.

Ожидаемо:

- тип лида — **целевой**;
- компания — «Альфа-Логистик»;
- в известных данных есть 40 рабочих мест, мебель, бюджет и контакты;
- в «чего не хватает» контакта нет — он уже указан в форме;
- человек не требуется;
- в черновике ответа нет выдуманных цен и сроков.

### Сценарий 2 — мало данных

«Сколько стоят офисные кресла? Нужно несколько штук», контакт заполнен.

Ожидаемо:

- тип лида — **целевой** (запрос про продукт компании);
- в «чего не хватает» — точное количество (модель может добавить модель и сроки);
- в черновике 1–2 уточняющих вопроса;
- нет конкретных цен, если их не было во входных данных.

### Сценарий 3 — жалоба

Сорван срок поставки, клиент требует возврат предоплаты.

Ожидаемо:

- **нужен человек: да**;
- причина передачи заполнена;
- тип лида — **неясно** (это не новая покупка);
- в известных данных перечислены факты жалобы;
- следующий шаг — передать жалобу менеджеру;
- черновик ответа нейтральный, без обещаний возврата и сроков.

### Дополнительная проверка

Заполните форму заявкой не по теме, например: «Продаю шины, есть ли у вас скидка?».
Ожидаемо: тип лида — **нецелевой**.

### Проверка без ключа

Даже без ключа страница открывается, а при обработке появляется понятное сообщение
«GigaChat не настроен…». Это нормально: значит, интерфейс и сервер работают.

## 4. Если что-то не работает

| Сообщение | Что делать |
|---|---|
| «GigaChat не настроен» | Заполните `GIGACHAT_CREDENTIALS` в `.env` и перезапустите сервер. |
| «GigaChat отклонил ключ авторизации» | Скопируйте ключ заново, целиком, без слова `Basic` и кавычек. При необходимости создайте новый ключ. |
| «Не удалось проверить SSL-сертификат» | Запустите `python download_cert.py` и проверьте папку `certs`. Если используется антивирус или прокси с проверкой HTTPS, добавьте его корневой сертификат в доверенные Windows или в `GIGACHAT_CA_BUNDLE_FILE`. |
| «Превышен лимит запросов» | Подождите минуту. Лимиты и остаток токенов видны в личном кабинете GigaChat. |
| «GigaChat не ответил за отведённое время» | Проверьте интернет и попробуйте снова. |
| «Битрикс24 не настроен» | Заполните `B24_URL` в `.env` и перезапустите сервер. |
| «CRM в неподдерживаемом режиме» | Переключите Битрикс24 в простой режим CRM без лидов. |
| «Поля сделки/контакта не созданы» | Запустите `python setup_bitrix24.py` и перезапустите сервер. |
| «Не удалось сохранить в Битрикс24» | Проверьте, что вебхук активен и имеет права `crm`, `task`, `im`. |
| Битрикс24 отвечает 429/503 | Приложение повторит запрос 2 раза с паузой. Если ошибка осталась, подождите и проверьте портал. |
| Порт 8000 занят | Измените `APP_PORT` в `.env`, например на `8001`, и откройте новый адрес. |
| `python` не найден | Переустановите Python с python.org, отметив «Add python.exe to PATH». |
| Страница не открывается | Убедитесь, что сервер запущен и в терминале нет ошибок. |

Логи приложения выводятся в терминал, где запущен `python run.py`. Ключ в логи
не попадает.

## 5. Интеграция с Битрикс24

Интеграция включается, когда в `.env` заполнен `B24_URL`. Используется простой
режим CRM без лидов:

- **контакт** — карточка клиента, в ней хранится снимок последней заявки;
- **сделка** — конкретная заявка;
- **таймлайн контакта** — история обращений;
- **задача** — по умолчанию создаётся только для заявок, где `needs_human=true`;
- **уведомление** — приходит ответственному через `im.notify`.

### Что и куда сохраняется

Стандартные поля контакта:

| Данные формы | Поле контакта |
|---|---|
| Имя | `NAME` |
| Телефон | `PHONE` |
| Почта | `EMAIL` |

AI-поля сделки и контакта:

| Данные AI | Сделка | Контакт (последняя заявка) |
|---|---|---|
| Компания | `UF_CRM_AI_COMPANY` | `UF_CRM_AI_LAST_COMPANY` |
| Суть запроса | `UF_CRM_AI_SUMMARY` | `UF_CRM_AI_LAST_SUMMARY` |
| Тип лида | `UF_CRM_AI_LEAD_TYPE` | `UF_CRM_AI_LAST_LEAD_TYPE` |
| Известные данные | `UF_CRM_AI_KEY_DATA` | `UF_CRM_AI_LAST_KEY_DATA` |
| Чего не хватает | `UF_CRM_AI_MISSING_DATA` | `UF_CRM_AI_LAST_MISSING_DATA` |
| Следующий шаг | `UF_CRM_AI_NEXT_STEP` | `UF_CRM_AI_LAST_NEXT_STEP` |
| Черновик ответа | `UF_CRM_AI_REPLY_DRAFT` | `UF_CRM_AI_LAST_REPLY_DRAFT` |
| Нужен человек | `UF_CRM_AI_NEEDS_HUMAN` | `UF_CRM_AI_LAST_NEEDS_HUMAN` |
| Причина | `UF_CRM_AI_HUMAN_REASON` | `UF_CRM_AI_LAST_HUMAN_REASON` |
| Исходный текст | `UF_CRM_AI_SOURCE_TEXT` | `UF_CRM_AI_LAST_SOURCE_TEXT` |
| Модель | `UF_CRM_AI_MODEL` | `UF_CRM_AI_LAST_MODEL` |
| ID запроса | `UF_CRM_AI_REQUEST_ID` | `UF_CRM_AI_LAST_REQUEST_ID` |
| ID сделки | — | `UF_CRM_AI_LAST_DEAL_ID` |
| Дата и время | — | `UF_CRM_AI_LAST_REQUEST_AT` |

В сделке также заполняются `title`, `contactId` и `comments` с полной карточкой.
Комментарий в таймлайне контакта дублирует краткую историю обращения и содержит
ссылку на сделку.

### Настройки в `.env`

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `B24_URL` | — | URL входящего вебхука. Без него интеграция выключена. |
| `B24_RESPONSIBLE_ID` | владелец вебхука | Ответственный за контакт, сделку и задачу. |
| `B24_SOURCE_ID` | `WEB` | Источник в справочнике Битрикс24. |
| `B24_CATEGORY_ID` | `0` | Воронка сделки. |
| `B24_STAGE_ID` | первая стадия | Стадия новой сделки. |
| `B24_TASK_MODE` | `needs_human` | `always`, `needs_human` или `never`. |
| `B24_NOTIFY_MODE` | `all` | `all`, `needs_human` или `never`. |
| `B24_TIMELINE_COMMENT` | `true` | Добавлять комментарий в таймлайн контакта. |
| `B24_TIMEOUT` | `10` | Таймаут одного REST-запроса в секундах. |

### Ограничения и устойчивость

- Используется не чаще ~2 запросов в секунду. Повторяются только ответы
  `429` и `503`; после таймаута создания сделки автоматического повтора нет,
  чтобы не создать дубликат.
- Контакт ищется по телефону, затем по email. Если поиск дубликатов недоступен,
  контакт не создаётся вслепую: сделка сохраняется без привязки, а в ответе
  появляется предупреждение.
- Если сделка не создалась, AI-поля контакта всё равно обновляются. Если не
  создались пользовательские поля, данные последней заявки записываются
  в комментарий контакта, а в ответе будет предупреждение.
- Задача создаётся только при наличии привязки к сделке или контакту. В задачу
  передаются `D_<dealId>` и `C_<contactId>`.
- Уведомление отправляется через `im.notify` с `TYPE=SYSTEM`.

### Проверка интеграции

```powershell
python setup_bitrix24.py
python -m unittest discover -s tests -v
```

После успешной заявки на странице появится зелёный блок «Сохранено
в Битрикс24» со ссылками на контакт и сделку. Если часть шагов не удалась,
блок будет жёлтым или красным и покажет безопасные предупреждения.

## 6. Как устроено внутри

```
intens2010/
├── app/
│   ├── main.py        # сервер: страница, /api/analyze, /api/health
│   ├── anonymizer.py  # замена ПДн на токены и восстановление значений
│   ├── anonymization_log.py  # CSV-журнал без текста и персональных данных
│   ├── gigachat.py    # авторизация, запрос к модели, обработка ошибок
│   ├── bitrix24.py    # контакт, сделка, таймлайн, задача, уведомление
│   ├── prompt.py      # системный промпт и JSON-схема ответа
│   └── schema.py      # проверка и нормализация ответа
├── static/
│   ├── index.html     # страница
│   ├── style.css      # оформление
│   └── app.js         # кнопки, индикатор, карточка и блок анонимизации
├── certs/             # сертификат Минцифры (создаётся download_cert.py)
├── logs/              # CSV-журнал анонимизации (создаётся автоматически)
├── tests/             # тесты анонимизации, журнала, пайплайна, API и Битрикс24
├── .env.example       # шаблон настроек
├── .env               # ваши ключи (не попадает в git)
├── download_cert.py   # помощник для сертификата
├── setup_bitrix24.py  # создание UF-полей в Битрикс24
├── run.py             # запуск одной командой
├── requirements.txt   # библиотеки
└── README.md
```

Поток данных:

1. Браузер отправляет данные формы (`name`, `phone`, `email`, `text`) на `POST /api/analyze`.
   Сервер склеивает их в текст заявки с подписями полей.
2. `app/anonymizer.py` заменяет персональные данные на токены: имя → `[ИМЯ_1]`,
   телефон → `[ТЕЛЕФОН_1]`, email → `[EMAIL_1]`, адрес → `[АДРЕС_1]`, паспорт →
   `[ПАСПОРТ_1]`, СНИЛС → `[СНИЛС_1]`, ИНН → `[ИНН_1]`, карту → `[КАРТА_1]`,
   дату рождения → `[ДАТА_РОЖДЕНИЯ_1]`, компанию → `[КОМПАНИЯ_1]`. Соответствие
   «токен → значение» хранится только в памяти текущего запроса.
3. Сервер получает access token в GigaChat (действует 30 минут, кэшируется).
4. Модель получает системный промпт и **замаскированный** текст заявки. Ответ
   запрашивается по JSON-схеме (`response_format: json_schema`, `strict: true`) —
   это снижает риск «сочинения» и лишнего текста. Точный замаскированный текст
   возвращается в браузер (поле `anonymized_text`) и отображается в блоке
   «Что уходит в нейросеть» вместе со статистикой маскирования.
5. `schema.py` проверяет девять полей, приводит типы и применяет детерминированные
   страховки по **оригинальному** тексту (оригинал остаётся только на сервере):
   - заявка с признаками жалобы/конфликта всегда уходит человеку;
   - жалоба по заказу не помечается как новый целевой лид;
   - без телефона/email в «чего не хватает» добавляется контакт для связи;
   - приблизительное количество («несколько») превращается в «точное количество»;
   - для целевого лида без контакта следующий шаг начинается с уточнения контакта,
     а черновик ответа просит телефон или email;
   - из следующего шага жалобы убираются формулировки вроде «нейтральный ответ клиенту»;
   - в известных данных не остаётся пунктов «не указано».
6. Токены в ответе модели заменяются обратно на реальные значения.
7. Готовая карточка возвращается в браузер.
8. Если `B24_URL` задан, сервер ищет контакт по телефону/email через
   `crm.duplicate.findbycomm`. Если контакта нет — создаёт его через
   `crm.item.add`.
9. Создаётся сделка, привязанная к контакту. В сделку записывается полная
   AI-карточка, в контакт — снимок последней заявки `UF_CRM_AI_LAST_*`.
10. В таймлайн контакта добавляется комментарий. Для заявок с
    `needs_human=true` создаётся задача, ответственному отправляется
    уведомление через `im.notify`.
11. Ошибка CRM не прерывает анализ: карточка всё равно возвращается, а в поле
    `crm` приходят статус и безопасные предупреждения.

Для каждого запроса, в котором были замаскированы данные, в CSV-журнал
добавляется строка: время, `request_id`, статус, тип ошибки (если была), модель,
длины текста, счётчики по категориям, число невосстановленных токенов и SHA-256
замаскированного текста. Исходный и замаскированный текст в журнал не пишутся.
`request_id` также возвращается в ответе API, поэтому строку журнала можно
сопоставить с конкретной карточкой.

Поля карточки: `company`, `summary`, `lead_type`, `key_data`, `missing_data`,
`next_step`, `reply_draft`, `needs_human`, `human_reason`.

Модель по умолчанию — `GigaChat-2-Pro` (баланс качества и скорости). Если нужна
более быстрая и дешёвая обработка, укажите в `.env` `GigaChat-2`; если нужно
максимальное качество — `GigaChat-2-Max`.

## 7. Безопасность и персональные данные

Перед отправкой в GigaChat сервер заменяет персональные данные на токены:

- имя → `[ИМЯ_1]`;
- телефон → `[ТЕЛЕФОН_1]`;
- email → `[EMAIL_1]`;
- адрес → `[АДРЕС_1]`;
- паспортные данные → `[ПАСПОРТ_1]`;
- СНИЛС → `[СНИЛС_1]`;
- ИНН → `[ИНН_1]`;
- номер банковской карты → `[КАРТА_1]`;
- дата рождения → `[ДАТА_РОЖДЕНИЯ_1]`;
- название компании → `[КОМПАНИЯ_1]`.

Что распознаётся:

- поля формы «Имя клиента», «Телефон», «Почта» и явные подписи в тексте
  («Адрес:», «Паспорт:», «СНИЛС:», «ИНН:», «Дата рождения:»);
- телефоны в разных форматах, email (включая кириллические домены), адреса
  с улицей/домом/квартирой;
- паспорт, СНИЛС, ИНН и даты рождения;
- номера карт — по алгоритму Луна; значение после явной подписи
  «Номер карты:» маскируется в любом случае, чтобы не пропустить опечатку;
- названия компаний после явных маркеров: `ООО`, `АО`, `ИП`, «компания»,
  «фирма», «организация», «предприятие»;
- имена в свободном тексте — по маркерам («меня зовут…», «контактное лицо:…»),
  известному имени из формы, а также по эвристике: частое имя, отчество или
  типичный фамильный суффикс.

Соответствие «токен → реальное значение» хранится только в памяти текущего
запроса. Оно не пишется в логи, файлы или базу данных и исчезает после ответа.
После ответа модели токены заменяются обратно, поэтому менеджер видит обычную
карточку с контактами.

Ограничения текущего слоя:

- это эвристики на регулярных выражениях, а не полноценный DLP-класс;
- нестандартные форматы (иностранные документы, сложные адреса, имя без
  фамилии в середине предложения) могут не распознаться;
- название компании маскируется только после явного маркера (`ООО`, «компания»
  и т. п.); бренд без маркера может остаться в тексте;
- слой снижает риск утечки, но не заменяет полноценную защиту по 152-ФЗ.

Для демонстрации по-прежнему лучше использовать синтетические данные.

Проверить слой анонимизации:

```powershell
python -m unittest discover -s tests -v
```

### Журнал анонимизации

Сервер ведёт append-only CSV-журнал в `logs/anonymization.csv`. Файл создаётся
автоматически при старте, строка добавляется после каждого запроса, для которого
был подготовлен замаскированный текст. Колонки:

- `timestamp_utc`, `request_id`, `status`, `error_type`, `model`;
- `original_chars`, `masked_chars`, `total_masked`, `unresolved`;
- счётчики по категориям: `name`, `phone`, `email`, `address`, `passport`,
  `snils`, `inn`, `card`, `birth_date`, `company`;
- `masked_sha256` — хеш замаскированного запроса для аудита и сверки.

В журнал **не попадают** исходный или замаскированный текст, имена, телефоны,
email и другие реальные значения. Это позволяет разбирать статистику и находить
инциденты, не создавая вторую копию персональных данных. Папка `logs/` исключена
из git.

Настройки в `.env`:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `ANONYMIZATION_LOG_ENABLED` | `true` | Включить или отключить журнал. |
| `ANONYMIZATION_LOG_FILE` | `logs/anonymization.csv` | Путь к файлу относительно проекта или абсолютный. |

Посмотреть последние записи:

```powershell
Import-Csv logs\anonymization.csv | Select-Object -Last 10 |
  Format-Table timestamp_utc, request_id, status, total_masked
```

Если файл недоступен для записи, приложение пишет предупреждение в лог, но
продолжает обрабатывать заявки.

### Прочие меры безопасности

- Ключ хранится только в `.env`, не попадает в браузер, в код и в логи.
- `.env` исключён из git через `.gitignore`.
- `B24_URL` — тоже секрет. Модуль интеграции не пишет URL, токен, телефоны,
  email и payload в логи; логгер `httpx` приглушён до `WARNING`.
- В Битрикс24 сохраняются реальные персональные данные, потому что токены
  восстанавливаются до записи в CRM. Доступ к порталу и полям нужно ограничить
  настройками ролей Битрикс24.
- Для локального MVP CORS разрешён для всех источников. Перед публикацией
  ограничьте `allow_origins` конкретным доменом.

## 8. Ограничения MVP

На этом этапе сознательно **не делаем**:

- собственную базу данных: история заявок хранится в Битрикс24;
- авторизацию пользователей;
- мессенджеры и автоматический приём заявок;
- ограничение CORS: для локального MVP разрешены все источники;
- полноценную защиту персональных данных по 152-ФЗ: слой анонимизации
  эвристический и не заменяет DLP-систему;
- ротацию CSV-журнала: файл растёт без ограничения размера.

Интеграция рассчитана на простой режим CRM без лидов. В классическом режиме
приложение вернёт `unsupported_mode` и не будет создавать контакт и сделку.

Задача MVP — проверить гипотезу: ускоряет ли ИИ первичную обработку заявки
и не теряет ли важные детали.
